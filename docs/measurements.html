Measurements

This page contains information regarding measurements.

WCET Estimation Methodology

This section describes how execution times are measured for functions in the AVR SD Safety Framework. The measurements are intended as input when selecting Task duration values. They are not formal WCET bounds.

Test conditions are selected by inspecting the source code and identifying a comparatively long relevant path through each function. Configuration-controlled functionality is enabled where it increases the executed work, and early-return paths are avoided unless they represent the relevant measured case.

Measurement Scope

The measurements cover all Tasks called by the Task Managers and all middleware diagnostic functions. The intervals corresponding to DUR_UNTIL_FIRST_SCHEDULE and DUR_UNTIL_NEXT_SCHEDULE are also measured.

Measurements are performed using the -O1, -O2, -O3 and -Os compiler optimization levels.

Measurement Setup

Two TCB peripherals configured in cascade mode count system-clock cycles. The timers are started immediately before the measured function and stopped immediately after it returns. The timer start and stop overhead is measured during initialization and subtracted from each result.

The target runs at a configured 20 MHz system clock and uses an explicit default fuse configuration. The compiler, DFP, target device and build environment are identified in the corresponding release notes.

Measurement Configuration

The measurement project is built with TEST. Several configuration options that are compile-time constants in a production build are variables in this build. Their checks are therefore evaluated at run time and may add a small amount of execution time.

The measurement configuration enables all optional startup diagnostics and all entries in the periodic latent-diagnostic queue. Periodic WDT and SWDT count diagnostics are enabled. Error reporting uses NOTIFICATION, and the notification log contains five entries.

Unless stated otherwise in the result table, underlying peripheral error flags are not set and state-dependent error-reporting paths are excluded. The result table identifies the relevant arranged state and any important exclusions.

Measurement Execution

Each function is called under the configured test conditions and measured once per compiler optimization level. Diagnostic return values and required setup or cleanup operations are checked. A failed diagnostic or measurement setup causes the measurement run to report FAIL.

Functions that intentionally reset the device or otherwise cannot provide a meaningful return measurement are reported as Not measured.

CRCSCAN Measurements

MW_DiagCrcScan is measured from function entry until return with global interrupts and the CRCSCAN ISR enabled. The result includes CRCSCAN setup, Idle sleep, CRC interrupt handling, result verification and cleanup under the fixed test configuration.

MW_ReportDiagCrcDone and T_HandleCrcInterrupt are measured inside the CRCSCAN ISR. ISR entry and exit are therefore excluded from these individual measurements. T_HandleCrcInterrupt is measured for regular Flash-scan completion and diagnostic completion, and the largest result is reported.

T_VerifyFlashIntegrity is not measured because its elapsed time depends on the configured Flash sections, CRC configuration, sleep and interrupt timing.

Measurement Results

The result table contains the measurements for -O1, -O2, -O3 and -Os, the maximum measured value and a comment describing the relevant test conditions.

The maximum is the largest valid measurement across the compiler optimization levels. Default Task durations are conservative overestimates based on this value. The selected defaults are provided in tasks_config.h, or in the corresponding example configuration where applicable. The System Integrator should adjust these values for the final application configuration and timing requirements.

Measurement Limitations

The results apply to the documented configuration and measured paths. They do not include application execution between Task Manager calls, unrelated interrupts, scheduling delays or state-dependent error handling unless explicitly stated.

Measurements that include waiting for a hardware diagnostic to complete can vary with peripheral-clock and analog operating conditions.

The measurements do not demonstrate that every feasible execution path has been exercised and must not be treated as formal WCET bounds.

Stack Depth Estimation Methodology

This section describes how the stack depth of the Safety Framework is estimated and how the measurement results should be interpreted.

The Safety Framework uses a layered call structure without recursion or run-time-sized stack allocation. Calls proceed from the Task Managers through Tasks, middleware and drivers without looping back through the call hierarchy. The normal call-chain depth is therefore bounded.

Interrupts can add further call chains on top of the interrupted code. The measurement calculates the deepest base call chain and the stack depth of each Interrupt Service Routine separately, then combines them according to the supported interrupt nesting.

Measurement Scope

The analysis covers the Safety Framework code reached from main, pre-startup, the Task Managers and the Framework Interrupt Service Routines. All optional startup diagnostics and all entries in the periodic latent-fault diagnostic queue are enabled.

Application code and Application Interrupt Service Routines are not included.

Measurements are performed using the -O1, -O2, -O3 and -Os XC8 compiler optimization levels.

Measurement Method

The Safety Framework is compiled using XC8 with the -fstack-usage option. The generated stack-usage information provides the stack frame size of each compiler-generated function.

The linked ELF file is disassembled using avr-objdump. The disassembly is used to determine the stack usage of assembly functions and reconstruct the calls between functions.

The stack depth of each call chain is calculated by adding the function stack frames and the two-byte return address added by each function call. Tail calls reuse the caller's stack frame and do not add a return address. Interrupt measurements also include the program counter stored by the interrupt hardware and the registers saved when entering the Interrupt Service Routine.

Calls through Schedules, callback tables and handler tables are resolved using the contents of the linked build. The analysis fails if a call cannot be resolved, a function has no calculated stack usage, or recursion or run-time-sized stack allocation is detected.

The XC8 -mchp-stack-usage analysis is also generated. It cannot calculate the complete Safety Framework stack depth because calls to functions written in assembly are reported as indeterminate stack adjustments. The measurement method has been verified against -mchp-stack-usage using call chains containing only compiler-generated functions, where both methods produce the same result.

Measurement Results

The result table contains one column for each compiler optimization level. The Max Stack Depth column contains the largest value across these optimization levels.

Base context is the deepest call chain reached from main or pre-startup without an interrupt.

Each ISR row contains the deepest call chain reached from that interrupt entry point.

Base context, deepest ISR and NMI combines the deepest base call chain, the deepest maskable ISR and the NMI. This applies when no interrupt vector is assigned to priority level 1, since two maskable interrupts cannot then be active at the same time.

Base context, two deepest ISRs and NMI also includes a second maskable ISR. This applies when an interrupt vector is assigned to priority level 1 using INIT_INT_LVL1. This result is used when defining the documented INIT_STACK_LIMIT.

Measurement Limitations

The results apply to the compiler, DFP, build configuration and Safety Framework version identified in the corresponding release notes.

The combined results are conservative overestimates because they assume that each interrupt occurs at the point of greatest stack usage in the preceding context, with the non-returning NMI occurring last, and do not account for critical sections or other states that may prevent the assumed nesting. The stack depth reached during normal execution is therefore likely to be significantly lower.
